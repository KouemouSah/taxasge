System Architecture

Facil is a monorepo-based platform with 4 packages: a Python/FastAPI backend, a Next.js frontend, and two Expo React Native mobile applications. This document details the architecture of each layer.

The platform follows a strict separation of concerns with the backend serving as a stateless REST API consumed by multiple clients (web frontend, two mobile apps). All state is stored in PostgreSQL with Redis as a performance cache layer. External services include Vertex AI for intelligence features and BANGE for payment processing.

Backend 3-Tier Architecture #

The backend follows a strict 3-tier layered architecture within each of its 30 feature modules. Each layer has a single responsibility and communicates only with its adjacent layer.

API Layer

The API layer consists of 62 FastAPI routers registered in app/main.py. Each router:

  • Defines HTTP endpoints with type-annotated parameters
  • Applies authentication and permission decorators (@permission_required)
  • Validates input via Pydantic v2 models
  • Delegates to the service layer for business logic
  • Returns structured JSON responses with error codes
# Example: API route pattern
from fastapi import APIRouter, Depends
from app.modules.auth.dependencies import get_current_user

router = APIRouter()

@router.get("/fiscal-services/{service_id}")
async def get_service(
    service_id: int,
    user = Depends(get_current_user),
    db = Depends(get_db)
):
    service = await fiscal_service_service.get_by_id(db, service_id)
    return service

Service Layer

Services contain all business logic, validation, and coordination between repositories. They handle transaction management, event publishing, and cross-module orchestration.

Repository Layer

Repositories are the only layer that interacts with the database. All queries use parameterized SQL with $1, $2 placeholders (never string formatting) for SQL injection prevention. 

# CORRECT: parameterized query
query = "SELECT * FROM users WHERE email = $1 AND status = $2"
row = await db.fetchrow(query, email, "active")

# NEVER: string formatting (SQL injection risk)
# query = f"SELECT * FROM users WHERE email = '{email}'"

Application Startup Sequence

The FastAPI application initializes in this order during startup (defined in main.py lifespan):

  1. Database pool — asyncpg connection pool (5-20 connections)
  2. Permissions sync — RBAC auto-discovery, role sync, obsolete cleanup
  3. Workflow sync — Python workflow classes synced to database (tariffs, docs, menus)
  4. Event Bus — Registers notification, audit, agent queue, payment assignment, and verification handlers
  5. Orphan repair — Self-healing for PAID requests not assigned to agents
  6. Cache system — Upstash Redis with in-memory fallback
  7. RBAC listener — PostgreSQL NOTIFY for real-time permission invalidation
  8. Internal scheduler — Cron jobs (replaces Cloud Scheduler)

Database Architecture #

PostgreSQL hosted on Supabase serves as the primary data store. The schema includes 145 tables organized across 10 domains, with pgvector extension for AI embedding storage.

Database Connection Architecture

▼

▼
PostgreSQL 15 (Supabase)145 tables + 50 enums + pgvector

Key database features:

  • Connection pooling: asyncpg pool with 5-20 connections, auto-reconnect
  • Lock ordering: Canonical lock sequence for bundle payments to prevent deadlocks
  • Soft deletes: deleted_at timestamp pattern on applicable tables
  • Audit trail: created_at, updated_at on all tables
  • pgvector: For RAG chatbot embedding storage and similarity search
  • tsvector: Full-text search on fiscal services catalog

See Database Schema Reference for the full table catalog.

Caching Architecture #

The HybridCache system (app/core/cache.py) provides Redis (Upstash TLS) as primary cache with automatic in-memory fallback when Redis is unavailable.

Cache InstanceFactory FunctionTTLPurpose
Defaultget_cache()5 minGeneral-purpose caching

Permissionsget_permissions_cache()10 minRBAC permission sets per user
Servicesget_services_cache()1 hourFiscal services catalog (873 items)

Workflow Mappings—30 minWorkflow menu mapping rules

Additional cache features:

  • Rate limiting: check_rate_limit(identifier, endpoint, max_requests, window_seconds)
  • Cache invalidation: invalidate_user_permissions_cache(user_id) triggered by PostgreSQL NOTIFY
  • RBAC listener: Real-time cache invalidation via app/core/rbac_listener.py subscribed to PostgreSQL NOTIFY channel
  • Decorators: @cached(cache_getter, ttl) for transparent result caching

The AI system uses Gemini 2.5 Flash via Google Vertex AI with a Retrieval-Augmented Generation (RAG) pipeline. It supports 35 specialized tools (19 public, 8 authenticated, 8 deep reasoning) and 5 role-based agent configurations. The self-reflection loop scores each response and regenerates if quality is below 5/10.

Internal Scheduler

The internal_scheduler (app/core/scheduler.py) runs periodic tasks within the application process, replacing the need for an external Cloud Scheduler:

  • Appointment hold expiration (15-minute TTL cleanup)
  • SLA deadline monitoring and escalation
  • Agent workload rebalancing
  • Cache warm-up for frequently accessed data
