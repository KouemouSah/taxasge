Mobile Publishing — Play Store, EAS Cloud, GitHub Actions

End-to-end tutorial for shipping the Facil citizen app (com.taxasge.app) and the Facil Inspector app (com.facil.inspeccion) to the Google Play Store. Covers Google Play developer verification (the 2024+ ADI registration flow), EAS-managed signing keys, GitHub Actions fallback builds, and the eas submit automation. Every command is reproducible from a clean checkout. Apple App Store paths are stubbed pending the Apple Developer Account (V1.1).

1. Architecture overview #

The Facil mobile publishing pipeline has four moving parts: GCP (secret storage, service account), Expo / EAS Cloud (canonical build + submit), GitHub Actions (orchestration + native fallback build), and Google Play Console (developer verification + release tracks). Each layer is independent and replaceable, but the canonical happy path is: push a tag → EAS Cloud builds the AAB → eas submit uploads it to Play Console internal track.

3. Play Developer service account #

eas submit uploads AABs to Play Console using a Google service account with the "Manage testing tracks" role. The SA is stored once in GCP Secret Manager and mirrored to GitHub + EAS so all three layers can authenticate with the same identity.

3.1 Create the service account (one-off)

# In GCP project taxasge-dev
gcloud iam service-accounts create play-publisher \
  --display-name="Play Publisher" \
  --description="EAS Submit upload of AABs to Google Play" \
  --project=taxasge-dev

# Generate a JSON key
TMP_KEY=$(mktemp --suffix=.json)
gcloud iam service-accounts keys create "$TMP_KEY" \
  --iam-account=play-publisher@taxasge-dev.iam.gserviceaccount.com \
  --project=taxasge-dev

# Store in GCP Secret Manager
gcloud secrets create google-play-service-account \
  --replication-policy=automatic \
  --project=taxasge-dev
gcloud secrets versions add google-play-service-account \
  --data-file="$TMP_KEY" \
  --project=taxasge-dev
rm -f "$TMP_KEY"

3.2 Invite the SA to Play Console

  1. Play Console → Users and permissions → Invite new user
  2. Email: play-publisher@taxasge-dev.iam.gserviceaccount.com
  3. App access → Facil → permission "Manage testing tracks" only
  4. Wait up to 24 h for permission propagation before the first eas submit

3.3 Mirror the SA to GitHub + EAS

# GitHub Secret (consumed by mobile-eas-submit.yml)
gcloud secrets versions access latest \
  --secret=google-play-service-account \
  --project=taxasge-dev \
  | base64 -w0 \
  | gh secret set GOOGLE_PLAY_SA_JSON_BASE64 --repo=KouemouSah/taxasge

# EAS Credentials (consumed by `eas submit` directly)
# Manual step: https://expo.dev/accounts/emacsah/projects/facil/credentials/android
#   → "Add a Google service account key" → upload the JSON file

3.4 Annual rotation

  1. gcloud iam service-accounts keys create a fresh JSON key
  2. gcloud secrets versions add to bump the GCP secret version
  3. Re-run the GitHub + EAS sync commands above
  4. Verify the new key works (dry run) then gcloud iam service-accounts keys disable the previous one
  5. After 7 days grace, gcloud iam service-accounts keys delete

4.3 Sync GitHub Secret with the EAS-managed keystore

When EAS regenerates the keystore (rotation, recovery), GitHub Actions still holds the previous one and silently produces an APK with a different signing fingerprint — rejected by Play Console. Re-sync via: 

# Download the EAS keystore + credentials
eas credentials --platform android  # interactive: pick "Build credentials" -> "Download keystore"
# Saved to ./@emacsah__facil-keystore.bak.jks

# Encode and push
base64 -w0 @emacsah__facil-keystore.bak.jks \
  | gh secret set ANDROID_KEYSTORE_BASE64 --repo=KouemouSah/taxasge

# Update password / alias / key password from the credentials.md file:
printf '<keystore-password>' | gh secret set ANDROID_KEYSTORE_PASSWORD --repo=KouemouSah/taxasge
printf '<key-alias>'          | gh secret set ANDROID_KEY_ALIAS         --repo=KouemouSah/taxasge
printf '<key-password>'       | gh secret set ANDROID_KEY_PASSWORD      --repo=KouemouSah/taxasge

5. Android Developer Verification (ADI token) #

Since 2024, Google requires every new developer account to prove ownership of each package name before any release track becomes available. The proof is a token file assets/adi-registration.properties embedded in a release-signed APK uploaded via "Validation des développeurs Android" → "Signer et importer un APK". Without it the entire Play Console UI for the package stays in Brouillon state.

5.1 Play Console flow

  1. Play Console → Validation des développeurs Android
  2. Register the package name (e.g. com.taxasge.app)
  3. Click "Sélectionnez une clé publique éligible" and paste the SHA-256 from §4.1 (must come from EAS — mismatch = silent rejection)
  4. Click "Signer et importer un APK" → copy the unique token snippet (e.g. CXZYNVIZWNFLAAAAAAAAAAAAAA)
  5. Build a release APK that contains the token (see §5.2)
  6. Upload the APK in the same dialog → Play Console verifies signature + token, then unlocks the standard release UI

5.2 Expo config plugin with-adi-registration

The token is injected at expo prebuild time by a tiny config plugin shipped under packages/mobile/plugins/with-adi-registration.js and packages/inspector/plugins/with-adi-registration.js. It writes the token to the right path on every prebuild so neither expo prebuild --clean nor a future EAS regeneration can wipe it. Token resolution order: ADI_REGISTRATION_TOKEN env var → hardcoded DEFAULT_TOKEN fallback. 

// packages/mobile/plugins/with-adi-registration.js (excerpt)
const { withDangerousMod } = require('@expo/config-plugins');
const fs = require('fs');
const path = require('path');

const DEFAULT_TOKEN = 'CXZYNVIZWNFLAAAAAAAAAAAAAA';

module.exports = function withAdiRegistration(config) {
  return withDangerousMod(config, ['android', async (cfg) => {
    const token = (process.env.ADI_REGISTRATION_TOKEN || DEFAULT_TOKEN).trim();
    if (!token) return cfg;  // inspector placeholder mode
    const dir = path.join(cfg.modRequest.platformProjectRoot, 'app', 'src', 'main', 'assets');
    fs.mkdirSync(dir, { recursive: true });
    fs.writeFileSync(path.join(dir, 'adi-registration.properties'), token + '\n');
    return cfg;
  }]);
};

Both plugins are registered as the last entry in app.json → expo.plugins: "./plugins/with-adi-registration".

5.3 Token rotation

Once Play Console accepts the verification, the token is useless to anyone else (it can only prove ownership of a package name whose signing key the bearer doesn't control). Treat it as near-public — the hardcoded fallback in the plugin is acceptable. If the upload key SHA-256 changes (rotation), re-issue the token via the same Play Console dialog and update either the DEFAULT_TOKEN constant or the ADI_REGISTRATION_TOKEN env var.

5.4 Inspector (V1.1)

The Inspector plugin ships in placeholder mode (no DEFAULT_TOKEN): when its env var ADI_REGISTRATION_TOKEN_INSPECTOR is unset, the plugin no-ops. To activate Inspector publishing later: register com.facil.inspeccion on Play Console, declare the EAS inspector key SHA-256, copy the new token, set the env var (EAS + GitHub Secret), trigger a build.

6. GitHub workflows reference #

Four workflows orchestrate the mobile pipeline. Three are explicit (EAS build, EAS submit, native fallback build); the fourth is a side-effect tagger that turns every push to develop into a versioned tag—know it exists or you will be confused by "why did a production build start when I only pushed docs?".

WorkflowTriggerOutputRequired secrets
mobile-eas-build.yml Manual dispatch (any profile/platform) or v*.*.* tag (production / Android) EAS-Cloud-built AAB or APK on expo.dev EXPO_TOKEN
mobile-eas-submit.yml Manual dispatch (track configurable) or workflow_run after a successful production build AAB pushed to Play Console internal track via eas submit EXPO_TOKEN, GOOGLE_PLAY_SA_JSON_BASE64
mobile-build.yml Push to develop/main with mobile changes or tag or manual Native Gradle APK (split: arm64 + armv7 + universal) + AAB, signed with the EAS upload key ANDROID_KEYSTORE_BASE64 + 3 password / alias / key-password secrets
auto-tag-mobile-inspector.yml Push to develop touching mobile or inspector source Auto-creates a v<next-patch> tag → cascades into mobile-eas-build.yml production None (uses default GITHUB_TOKEN)
inspector-build.yml Manual dispatch or inspector-v*.*.* tag EAS-Cloud-built APK or AAB for the Inspector app EXPO_TOKEN
inspector-ci.yml Push / PR with inspector changes TypeScript + ESLint gate (no artefact) None

6.1 Why mobile-build.yml exists alongside EAS

EAS Cloud is the canonical channel: reproducible toolchain, shared keystore, sourcemap upload to Sentry, env var management. mobile-build.yml is the fallback: when the monthly EAS quota is exhausted (30 builds / month on the free plan) or expo.dev is down, a fresh APK can be produced on a GitHub-hosted runner using the mirrored keystore. The workflow is hardened to fail fast on missing keystore secrets — it will never silently fall back to the debug key (which would produce an APK that looks signed but is rejected by Play Console).

6.2 The auto-tag side effect

auto-tag-mobile-inspector.yml creates a v<X.Y.Z> tag on every push to develop that touches mobile/inspector source. That tag triggers mobile-eas-build.yml with profile=production, consuming an EAS slot. To avoid surprise builds: keep developer-facing changes (config plugins, docs, secrets) confined to clearly identified pushes; or temporarily disable the workflow if you only want a TS-only push.

7. EAS environment variables #

EAS env vars are scoped per environment (development / preview / production) and per visibility (plain text / sensitive / secret). Use the CLI to manage them — the web UI exists but is fiddly: 

cd packages/mobile

# Plain text variable, all environments
eas env:create --name EXPO_PUBLIC_API_URL \
  --value https://taxasge-backend-staging-392159428433.us-central1.run.app \
  --visibility plaintext \
  --environment preview \
  --environment production

# Sensitive (read in build logs as ***)
eas env:create --name SENTRY_AUTH_TOKEN --value <token> --visibility sensitive \
  --environment preview --environment production

# Secret (never readable, only consumable)
eas env:create --name EXPO_PUBLIC_SENTRY_DSN --value <dsn> --visibility secret \
  --environment preview --environment production

8. Daily build & release workflow #

The happy path from a finished feature branch to a release on the Play Console internal track is six steps. Steps that touch shared state (push, tag, submit) are flagged SHARED: confirm before running them.

  1. Local validation: 
    cd packages/mobile
npm run type-check
npm run lint
# Optional: launch Expo Go to validate UX
npx expo start --tunnel
  2. Commit & push (SHARED) — the push triggers auto-tag-mobile-inspector.yml, which creates a tag v<next-patch>, which in turn fires the production EAS build. Allow ~25 minutes. 
    git push origin develop  # confirm with user before running
  3. Watch the EAS build on expo.dev or via API: 
    EXPO_TOKEN=$(gcloud secrets versions access latest --secret=expo-token --project=taxasge-dev)
curl -s -H "Authorization: Bearer $EXPO_TOKEN" \
     -H "User-Agent: eas-cli" \
     -H "Content-Type: application/json" \
     -X POST https://api.expo.dev/graphql \
     -d '{"query":"query{app{byFullName(fullName:\"@emacsah/facil\"){builds(limit:3,offset:0){id status buildProfile gitCommitHash artifacts{applicationArchiveUrl}}}}}"}'
  4. Submit to internal track (SHARED) via mobile-eas-submit.yml: 
    gh workflow run mobile-eas-submit.yml \
  --repo=KouemouSah/taxasge \
  -f track=internal
    The workflow fetches the latest production AAB and pushes it to the internal track via the play-publisher service account.
  5. Test internally on real devices via the Play Console internal-tester opt-in URL. Soft-launch with the QA team for 24 h.
  6. Promote to production: Play Console → Production → Promote release. Manual review by Google: 1 to 7 days.

8.1 One-off preview APK (sideload)

# Trigger a preview APK (no submit) via GitHub
gh workflow run mobile-eas-build.yml \
  --repo=KouemouSah/taxasge \
  -f profile=preview \
  -f platform=android

# Or directly via EAS CLI (locally, in packages/mobile/)
eas build --profile preview --platform android --non-interactive --no-wait

8.2 Native fallback (EAS quota exhausted)

# Manual dispatch — build APK + AAB on a GitHub-hosted runner
gh workflow run mobile-build.yml \
  --repo=KouemouSah/taxasge \
  -f build_type=release

The artefacts land under Actions → Artifacts with names facil-apk-<ref>-<sha> and facil-aab-<ref>-<sha>. Signed with the EAS upload key (synced via §4.3).

9. Troubleshooting #

9.1 "The uploaded APK does not have the required token file"

The APK is missing assets/adi-registration.properties. Either the with-adi-registration plugin didn't run (check app.json → plugins), or the build predates §5.2. Trigger a fresh EAS preview build from a commit that contains the plugin.

9.2 Play Console rejects the upload silently

Likely a signing-key mismatch: the APK was signed with a key whose SHA-256 differs from the eligible public key declared in Play Console. Run the cert-extract script under packages/backend/scripts/verify_apk_signature.py, compare with the value at expo.dev → Credentials, and re-declare on Play Console via "Changer de clé" if needed.

9.3 CI APK signed with debug key

Symptom: APK fingerprint starts with FA:C6:17:45:... (Android debug keystore default). Means ANDROID_KEYSTORE_BASE64 + 3 password secrets are missing or stale. The hardened mobile-build.yml now fails fast on this; if the failure mentions "silently fall back to debug signing", re-run §4.3.

9.4 EAS quota exhausted

Free EAS plan: 30 builds / month / org. Falls back to long queue. Three options: (1) wait for the next billing cycle; (2) upgrade the EAS plan; (3) use the native mobile-build.yml path (§8.2). The artefact is identical (same upload key).

9.5 expo prebuild --clean wipes my Android customisations

The committed android/ folder is the source of truth in this repo (non-CNG mode). Never run --clean: it deletes hand-edited files (e.g. build.gradle tweaks, the ADI token, custom signing config). Use npx expo prebuild --no-install instead. mobile-build.yml was hardened to drop the --clean flag in commit afffdfe4.

9.6 "This service account has not been granted access" from eas submit

The play-publisher SA must be invited to Play Console with the "Manage testing tracks" role on the Facil app, AND Google must have propagated the permission (up to 24 h). Verify with gcloud secrets versions access latest --secret=google-play-service-account --project=taxasge-dev | jq '.client_email' then check the email under Play Console → Users and permissions.

9.7 Production build fired from a docs-only push

auto-tag-mobile-inspector.yml reacts to every push to develop that changes mobile/inspector source. To prevent the side effect on a single push, edit .github/workflows/auto-tag-mobile-inspector.yml → paths-ignore to skip docs / config-plugin-only changes, or revert the side-effect tag with git push origin :v<X.Y.Z> after the fact (cancels the in-flight EAS build).

9.8 iOS profiles fail with "no Apple credentials"

iOS is gated off in V1 — expected. Provision the Apple Developer account, run eas credentials --platform ios in packages/mobile, upload the App Store Connect API key (.p8), then set MOBILE_BUILD_PLATFORM=all in repo Variables. The workflow honours this var on tag pushes.
