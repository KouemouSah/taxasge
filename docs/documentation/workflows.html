Wizard Step Flow #

Every service request follows a wizard with configurable steps. The standard flow is:

Selection → Upload → Form Review 1..N → Appointment → Payment → Confirmation
StepPurposeOptional?
SelectionChoose sub-type, person type, motivo (reason). Drives dynamic form visibility.No (always present)
UploadUpload required documents (OCR extraction runs here). Documents vary by workflow.No
Form Review 1..NReview OCR-extracted data, fill manual fields, validate business rules.Count varies (1-3)
AppointmentBook appointment slot (holds + reservations). Only for workflows requiring in-person visit.Yes
PaymentCalculate fee and initiate payment (BANGE or manual).No
ConfirmationSummary display, PDF download, email with receipt.No

Cache-First Wizard

The wizard uses a cache-first approach: step data is stored in Redis during the wizard flow (no database writes until payment). The POST /wizard-sessions/{id}/initiate-payment endpoint performs an atomic persist-and-pay operation in a single database transaction.

ConditionEvaluator #

The ConditionEvaluator dynamically controls step and section visibility based on form data collected in earlier steps. Conditions are defined as JSON objects in workflow configurations.

Critical Rule: Conditions Are Always Strings

Conditions must use string values: {"is_minor": "true"}, not {"is_minor": true}. The frontend RadioGroup stores strings, and the ConditionEvaluator performs strict == comparison. 

# Condition example in workflow config
{
  "section_id": "minor_documents",
  "visible_when": {"is_minor": "true"},
  "documents": ["autorizacion_parental", "certificado_nacimiento"]
}

Entity Routing #

Entity routing is entirely database-driven. The entities.workflow_codes JSONB column determines which entity handles which workflow. This is managed via the admin UI, with no code changes required.

No Code Routing

Never create get_issuing_entities() functions in code. The entity_code field on PredefinedWorkflow is declarative/audit only. Actual routing is resolved from entities.workflow_codes at runtime.

Appointment Management #

Appointment-enabled workflows use a 2-table system to prevent double-booking:

TablePurposeLifetime
appointment_holdsTemporary hold during wizard flow15 minutes TTL
appointment_reservationsPermanent confirmed reservationPermanent

Three SQL functions manage the appointment lifecycle:

  • hold_appointment_slot() — Creates temporary hold, counts held+confirmed
  • confirm_appointment_hold() — Converts hold to confirmed + INSERT reservation
  • get_available_slots_v3() — Returns available slots (counts reservations + holds)

2-Layer Validation #

Validation Architecture
Layer 1: Upload StepSchemaValidationEngine (70+ JSON rules) + RiskAnalyzer (12 steps)
▼
Layer 2: Form Review Stepvalidate_step() overrides only (real Python)
  • Schema (Layer 1) = Document validity (format, signatures, required fields, temporal validity)
  • validate_step (Layer 2) = Business decision (what the result means for THIS workflow)
  • Never duplicate rules between layers. If schema has certificado_vigente, do not recreate in validate_step.
