Atomic Payment Pipeline #

The POST /wizard-sessions/{id}/initiate-payment endpoint performs all operations in a single database transaction. If any step fails, everything rolls back.

1. Read Redis session → 2. Validate data → 3. BEGIN TX → 4. INSERT service_request → 5. Upload docs to Firebase → 6. INSERT service_payment → 7. Confirm appointment → 8. COMMIT
Zero orphaned records

The atomic pipeline ensures that a service request is never created without its associated payment, and vice versa. Failed document uploads trigger a complete rollback.

Bundle Payment Flow #

Bundle payments handle commercial license obligations spanning multiple government entities. A single commercial license may generate obligations to TESORO, AYUNTAMIENTO, CAMARA_COMERCIO, and various MIN_* ministries.

Commercial License → Classification → Zone Resolution → Obligation Generation → Multi-Entity Validation → Payment → Receipt

Multi-Entity Validation

Each entity validates its portion of the bundle independently. The TESORO entity validates overall financial compliance, AYUNTAMIENTO validates municipal requirements, and CAMARA_COMERCIO verifies commercial registration status.

Lock Ordering (Concurrency) #

Deadlock Prevention

For any transaction touching commercial licenses AND field payments, the following canonical lock order MUST be followed. Violating this order causes deadlocks under 100+ concurrent agents.

  1. commercial_licenses — SELECT ... FOR UPDATE (the only explicit lock — root entity)
  2. service_requests — INSERT only (optimistic via partial UNIQUE index, no FOR UPDATE)
  3. license_obligations — UPDATE batch (locks acquired automatically)
  4. service_payments — INSERT final
-- Always set transaction-scoped timeouts at the start
SET LOCAL lock_timeout = '3s';
SET LOCAL statement_timeout = '5s';
Never FOR UPDATE on service_requests

Concurrency on service_requests is handled by the partial unique index idx_sr_commercial_license_unique plus try/except asyncpg.UniqueViolationError recovery (deterministic SELECT by commercial_license_id).

Receipt Generation #

PDF receipts are generated using the SummaryPDFService with the citizen_summary_pdf.html template (490 lines). Receipts include:

  • Entity name and city in the header
  • Fiscal service details per obligation
  • Calculated amounts with breakdown
  • Payment reference and timestamp
  • QR code for receipt verification

Receipt Security & QR Verification #

Every receipt, license, certificate, and service-request PDF generated by Facil is cryptographically signed and publicly verifiable via QR code. The QR encodes a deep-link to a public verification endpoint; the link carries an HMAC-SHA256 token that is impossible to forge without the server-side secret. Tampering with the receipt number, the amount, or the date breaks the signature — the verification endpoint then rejects the document.

What makes the document infalsifiable

Security ControlImplementationWhy it matters
Cryptographic algorithm HMAC-SHA256 Standard authenticated digest. Forging a valid token requires the server secret — computationally infeasible without it.
Signing secret RECEIPT_VERIFICATION_SECRET → JWT_SECRET_KEY (fallback) Permanent secret loaded from environment / Secret Manager. Never the ephemeral SECRET_KEY (which would rotate on every Cloud Run cold-start and invalidate old QR codes).
Signed message receipt_number | amount | YYYYMMDD Binds the token to the exact receipt, exact amount, and the day of payment. Edit any field on the PDF → signature breaks → verification fails.
Comparison hmac.compare_digest(expected, provided) Constant-time comparison — immune to timing side-channel attacks that could otherwise leak the token byte-by-byte.
Token format 16-character hex (first 64 bits of the HMAC) Compact enough for a small QR code (ERROR_CORRECT_M still scannable on a phone), large enough to make brute-force search infeasible (2^64).
Public endpoints GET /api/v1/verify/{ref} · /request/{ref} · /license/{ref} · /certificate/{ref} No authentication required — anyone (third party, bank teller, customs officer) can scan and verify in one tap. Privacy is preserved: response only confirms validity + minimal payment data.
Storage & vault service_payments · payment_receipts · uploaded_files (vault) PDF persisted to Firebase Storage with signed URL and registered in the citizen vault. The QR is verified against live DB state, so a revoked / refunded payment can be flagged at scan time.

Threat model

  • Editing the printed PDF (changing the amount, name, or date in a PDF editor) → QR token no longer matches the new content → verification endpoint returns 404. Detected on first scan.
  • Reusing a QR for another receipt → the verification endpoint loads the receipt by its number, not by the token; a stolen token cannot be paired with a different receipt number.
  • Brute-forcing a token → 264 search space, public endpoint behind rate-limit. Statistically infeasible.
  • Timing side-channel → mitigated by hmac.compare_digest().
  • Secret leak → rotate RECEIPT_VERIFICATION_SECRET in Secret Manager — old receipts must then be re-signed if continued verification is required (acceptable trade-off for security incidents).
