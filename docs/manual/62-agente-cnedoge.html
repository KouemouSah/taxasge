Patrón común agentes workflows simples (CNEDOGE / DGT / Extranjería)

Los agentes de las entidades CNEDOGE (pasaporte), DGT (licencia de conducir) y Extranjería (residencia y visado) comparten exactamente las mismas acciones, la misma UI y los mismos endpoints backend (app/modules/service_requests/api/agent_routes.py). La única diferencia es el workflow Python concreto ejecutado (pasaporte_workflow_v2.py vs conducir_workflow.py vs residencia_workflow.py / tramites_visado_workflow.py) qui determina los documentos requeridos, las validaciones específicas y los pasos del wizard ciudadano. Esta página describe el patrón común, ilustrado con el ejemplo detallado de la licencia de conducir (DGT), y proporciona 3 mini-fichas de especificidad por entidad al final.

1. El patrón común: estados y ciclo de vida

Toda solicitud workflow simple sigue el mismo ciclo. El agente actúa sobre las solicitudes en estado pending_agent_review de su cola (filtrado por entity_code + workflow_code de los workflows que la entidad maneja, ver página 89). Estados clave :

┌─────────────────────────────────────────────────────────────────────┐
│  Patrón común agente workflows simples                              │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  pending_agent_review (cola entidad)                                │
│         │                                                           │
│         ▼  lock_for_review                                          │
│  locked_by_agent                                                    │
│         │                                                           │
│         │  El agente revisa la solicitud :                          │
│         │  - documentos OCR-extraídos (schemas correspondientes)    │
│         │  - resultados validate_step del workflow                  │
│         │  - cita programada (si requires_appointment)              │
│         │                                                           │
│         ├─ request_documents → waiting_documents                    │
│         │  (ciudadano completa el dossier)                          │
│         │                                                           │
│         ├─ escalate → escalated_supervisor                          │
│         │  (caso ambiguo o monto sensible)                          │
│         │                                                           │
│         ├─ reject → rejected (motivo obligatorio)                   │
│         │                                                           │
│         └─ approve → approved_by_agent                              │
│                  → (workflow continúa: payment, cita, completado)   │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘

2. Las 5 acciones disponibles del agente

Acción Endpoint backend Permiso Efecto
lock_for_review POST /service-requests/{id}/lock service_request.lock Estado → locked_by_agent; previene que otro agente trabaje en paralelo
approve POST /service-requests/{id}/decision service_request.approve Estado → approved_by_agent; el workflow avanza al paso siguiente (típicamente pago o cita)
reject POST /service-requests/{id}/decision service_request.approve Estado → rejected; rejection_reason obligatorio (max 500 chars). Notificación al ciudadano.
request_documents POST /service-requests/{id}/decision service_request.approve Estado → waiting_documents; lista de documentos faltantes ; el ciudadano puede recargar y resoumettre
escalate POST /service-requests/{id}/escalate service_request.escalate Estado → escalated_supervisor; el supervisor de la entidad toma el relais (ver página 71)

El campo decision del payload acepta exactamente uno de los tres valores: approve, reject o request_documents (regex backend : ^(approve|reject|request_documents)$). El endpoint escalate está separado para tracking distinto.

3. Ejemplo detallado: ConducirWorkflow (DGT)

La licencia de conducir DGT es un buen exemplo car ses étapes sont representativas de tous los workflows simples. Workflow class : ConducirWorkflow en app/modules/service_requests/workflows/conducir_workflow.py. Entidad : DGT (Dirección General de Tráfico Rodado y Seguridad Vial). requires_appointment=True (examen práctico ou retrait), requires_nota_ingreso=False (pago directo Mobile Money).

5 códigos workflow (1 clase Python, 5 workflow_codes)

workflow_code Caso de uso Solicitud type
CONDUCIR_NUEVOPrimera solicitud (incluye examen práctico)EXPEDICION
CONDUCIR_CANJEConversión de licencia extranjera (solo RESIDENT)sub_type CANJE
CONDUCIR_RENOVACIONRenovación de certificado caducado o por caducarRENOVACION
CONDUCIR_DUPLICADODuplicado por pérdida, robo o deterioro (motivo obligatorio)DUPLICADO
CONDUCIR_EXTENSIONExtensión a una nueva clase (no requiere nuevo examen)sub_type EXTENSION

7 clases de licencia con edad mínima

Definidas en el enum LicenseClass: A motos (18+), B vehículos ligeros <3.5T (18+), B+ ligeros + remolque (18+), C pesados >3.5T (21+), D pasajeros >9 plazas (21+), E articulados (21+), F especiales/agrícolas (18+). La clase AM (16+) está diferida a Phase 2. La clase COPIA_ADICIONAL no es gestionada por DGT (gestión Comisaría Policía).

Steps del wizard (visibles también para el agente)

  1. Step 0 selection — tipo de solicitud (NUEVO/CANJE/RENOVACION/DUPLICADO/EXTENSION) + applicant_type (CITIZEN_GQ con DIP o RESIDENT con NIE) + clases solicitadas.
  2. Step 1 upload_documents — documentos según el tipo: DIP/NIE, foto carnet, certificado médico, eventualmente licencia anterior (renovación/duplicado), certificado país origen (canje).
  3. Step 2 form_review_1 — datos personales extraídos del DIP/NIE por OCR; el ciudadano verifica y corrige.
  4. Step 3 form_review_2 — datos de la solicitud: tipo, clases, motivo (duplicado), país de origen (canje).
  5. Step 4 form_review_3 — verificación de documentos justificativos (secciones condicionales). Cross-validation del nombre para canje (matching licencia extranjera ↔ DIP/NIE).
  6. Step 5 appointment — RDV para examen práctico (NUEVO) o retrait (otros).
  7. Step 6 payment — pago directo Mobile Money BANGE (no hay Nota de Ingreso intermedia para DGT). Tarifa según tipo + clases.
  8. Step 7 confirmation — resumen + agent_checklist. El agente revisa antes de aprobar.

4. Especificidades por entidad (mini-fichas)

4.1 CNEDOGE — pasaporte

Workflow class : PasaporteWorkflow (4 códigos : PASAPORTE_EXPEDICION, PASAPORTE_RENOVACION, PASAPORTE_PERDIDA, PASAPORTE_DETERIORO). Documentos típicos : DIP, foto carnet, certificado de nacimiento, eventualmente declaración policía (pérdida/robo). Especificidad clave : requires_appointment=True + cita biométrica presencial obligatoria en oficina CNEDOGE — el ciudadano se presenta físicamente para captura de huellas y foto biométricas (datos directos para producción del pasaporte). No hay matching facial automatizado por algoritmo — la verificación de identidad es visual y firmada por el agente. El PDF del pasaporte se genera tras el RDV. requires_nota_ingreso=True para algunos sub_types (validación OCR del Nota antes del pago principal).

4.2 DGT — licencia de conducir

Cubierta en detalle en la sección 3 más arriba. Especificidad clave : examen práctico obligatorio para CONDUCIR_NUEVO (paso real fuera de la plataforma, programado vía el step appointment). 7 clases (A-F, sin AM/COPIA_ADICIONAL). Pago directo Mobile Money (sin Nota de Ingreso intermedia).

4.3 Extranjería — residencia + visado

Detalle completo : página 67. Especificidad clave : dos workflows distintos. ResidenciaWorkflow (2 códigos : RESIDENCIA_PRIMERA_VEZ + RESIDENCIA_RENOVACION) en 2 phases (Phase 1 dossier + stamps 2 500 XAF → Nota de Ingreso oficial papier → Phase 2 nota + pago 200K/100K + cita CNEDOGE para entrega física). TramitesVisadoWorkflow (4 sub_types : Prórroga 20K, Alternativo 20-600K tiered selon durée, Permanencia 50K/mes, Salida Vencido 30K/mes auto-calculado). Validation CEMAC (6 países sin visa) + 12 schemas OCR + 11 reglas validate_step.

5. Permissions del rol agente

Las permissions del agente se rattachent au rôle (agent_cnedoge_pasaporte, agent_dgt, agent_extranjeria, etc.), no a la entidad directamente. Permisos comunes :

  • service_request.view_assigned — ver la cola de solicitudes asignadas
  • service_request.lock — lock_for_review
  • service_request.approve — decisión approve/reject/request_documents
  • service_request.escalate — escalada al supervisor
  • service_request.verify_manually — verificar identificadores (DIP, NIF) — usado por Verify identidad

6. Aviso honestidad documental

Lo que NO existe en el código (mayo 2026)

A diferencia de descripciones genéricas previas en este manual, el patrón agentes workflows simples no incluye actualmente: reconocimiento facial automatizado o matching biométrico foto-DIP por algoritmo (la captura biométrica CNEDOGE es física, sin scoring auto), verificación INTERPOL automatizada, anulación automática de cita tras N ausencias del ciudadano (no hay lógica de tracking de absences en el código), naturalización gestionada por Facil (decreto presidencial hors scope). El patrón es genérico y simple : revisión documental + decisión humana + acciones backend estándar.
